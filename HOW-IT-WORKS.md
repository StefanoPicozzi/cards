# How it works

This page is the whole system in one place: the pieces, the life of a card, and every automated job, with where it runs and where its results go. Everything here is public, except the logins the test runner uses.

## The pieces

| Piece | Where | What it is |
| --- | --- | --- |
| Cards | [edgible-org/cards](https://github.com/edgible-org/cards), this repo | Self-hosted setups anyone can run. **App cards** (`metadata.type: app`) are one app each, always tested. **Pattern cards** (`metadata.type: pattern`) wire several apps together, built from app cards. |
| The format and tools | [edgible-org/card-kit](https://github.com/edgible-org/card-kit) | The card format (`card.schema.json`), and the tools that check, test, and document a card: `check-cards`, `check-env`, `test-card`, `test-cards`, `card-readme`, `card-image`, `card-icon`, `check-map`. |
| The agent skill | [card-kit/skills/edgible-cards](https://github.com/edgible-org/card-kit/tree/main/skills/edgible-cards) | Teaches an AI agent to go from a person's need to a running, published card, look after it, and contribute back. Works in Claude Code, Claude's apps, and other agents that read the Agent Skills format. |
| The needs map | [needs-map.yaml](https://github.com/edgible-org/card-kit/blob/main/skills/edgible-cards/needs-map.yaml), beside the skill | What people say they need, mapped to categories, the questions that decide the answer, how to publish safely, and the cards for it. Built on [awesome-selfhosted](https://awesome-selfhosted.net)'s categories, plus categories Edgible adds where that list has none yet, mostly AI tools. |
| The skill's tests | [card-kit/skills/edgible-cards/evals](https://github.com/edgible-org/card-kit/tree/main/skills/edgible-cards/evals) | Prompts the skill should and should not answer, held-out real prompts that answers are scored against, and the tool that measures triggering. |
| MCP | The [mcp-bridge](mcp-bridge) app card | Publishes any stdio MCP server over Streamable HTTP, so AI assistants reach it from anywhere. An Edgible MCP server for finding cards is built on it. |

Edgible itself is not here. Cards are free and portable; Edgible is the platform that publishes them: hostnames and TLS, auth modes, TCP and UDP, the device agent, and teams.

## The life of a card

1. **Someone needs it.** A person describes a need to an AI assistant with the skill, or opens a request issue. When no card fits, the skill shortlists apps from awesome-selfhosted and other current sources, and offers to build one.
2. **It is built and tested.** The author, often with an agent, writes the card from the closest existing one, and runs `test-card` on their own Edgible serving device. That runs the whole lifecycle (check the machine, start, publish, verify each hostname, the card's own checks, tear down) and writes `test.yml`.
3. **It is checked and reviewed.** The pull request runs `check-cards --fresh`: the schema, the conventions, the app-card rules, and that `test.yml` matches the files. A maintainer reviews what a test cannot judge, from the checklist in the pull request template, and runs `test-card` on an Edgible device before merging. The merge is the publish.
4. **It keeps being tested.** A card is retested when it changes, when one of its images has a newer version (a Renovate pull request is tested on a real device before it can merge), when Edgible releases a new version, on a rolling nightly schedule that takes a share of the cards each night, and on request (the Retest a card issue form). Every pinned image is also scanned for fixable vulnerabilities every night. The badge shows the result and the Edgible version, and `test.yml` the date. A failure opens an issue. How recent a card's test is depends on whether the nightly chain has been running, so read the date, not the page's promise.
5. **It is used, and it improves.** People run it from its README or through the skill. A problem found in use becomes a fix and a pull request, by the same path.
6. **It may be promoted.** An app card that passes for weeks, and that tags show many people keep running, can be packaged as a managed Edgible template. The card stays the source.

## The automated jobs

| Job | Trigger | Runs on | What it does | Results go to |
| --- | --- | --- | --- | --- |
| **cards** ([cards.yml](.github/workflows/cards.yml)) | Every pull request and push to `main` here | GitHub's own runners | `check-cards --fresh` on every card | The pull request's check |
| **kit** ([card-kit's kit.yml](https://github.com/edgible-org/card-kit/blob/main/.github/workflows/kit.yml)) | Every pull request and push to card-kit | GitHub's own runners | `check-cards` on every card here, so a change to the tools cannot break a card; `check-map` on the needs map | The pull request's check |
| **regression** ([regression.yml](.github/workflows/regression.yml)) | Nightly, when grow ends, and by hand with `force` or `only` | Three jobs. **plan**, on GitHub's own runners, picks tonight's cards and the runner labels each needs from its `places:`. **test** is one job per card on a fleet machine (label `edgible-test`: Docker, the `edgible` CLI signed in, and a serving device) with those labels, such as `mem-8g` for immich, so cards run in parallel on machines that fit. **collect**, on GitHub's runners, merges the results | `test-cards --spread 7 --plan`: tests a new or changed card that night, and spreads every other test (a new Edgible version, or a week without one) over the week, about a seventh of the cards a night, so a card comes round about once a week while the chain runs every night. Cards that publish the same app name share a job. With the `FLEET_TOKEN` secret (read access to the repo's runners), a card no machine online can run is left out rather than queued. Each test is the full lifecycle on a real device, and its status records the machine | The [`test-status` branch](https://github.com/edgible-org/cards/tree/test-status) (`status.json` and one badge file per card), and an issue for each failure |
| **grow** ([grow.yml](.github/workflows/grow.yml)) | Nightly, when the skill evals end, and by hand with an app name; makes up to 5 cards a night, one after another, each as a run of its own; skipped while 6 agent-made pull requests await review | Split by what each part needs: the hub (label `hub`) writes the card and fixes what `check-cards` finds; a fleet machine (`edgible-test`) checks it again and tests it, twice at most, with a fix on the hub between; GitHub's own runners open the pull request or issue. The card passes between them as workflow artifacts. Adding merged cards to the needs map stays on the Mac, which has a GitHub sign-in for card-kit | Picks the first gap in the needs map (`pick-app`), has an agent with the skill write one app card for the best-fitting app, fetches the app's icon, checks it with `check-cards --untrusted` (nothing that reaches outside the card), and tests it with `test-card`, with up to three fix attempts. The agent has its own home folder and a short list of commands, and no GitHub or Edgible login | A pull request labelled `agent-card` for a person to review, or an `app-request` issue saying how far it got. Nothing is merged automatically. Each run also opens a card-kit pull request adding merged agent cards to their category in the needs map |
| **fleet-test** ([fleet-test.yml](.github/workflows/fleet-test.yml)) | A maintainer adds the label `run-fleet-test` to someone else's pull request; a new push to the pull request removes the labels | Runs from `main`, never from the pull request. Checks that the sender can write to the repository, that the commit is still the one labelled, that only card folders changed (not `.github/` or the top level; three at most; no native card), and `check-cards --fresh --untrusted` on GitHub's own machine; only then fetches the card's files as data and runs `test-card` on a fleet machine | Comments the result with the commit it tested and adds `fleet-tested` on a pass. Commits nothing to the pull request. The fleet machines can publish apps, so nothing starts without the label: the label is a maintainer saying they read that commit |
| **daily-report** ([daily-report.yml](.github/workflows/daily-report.yml)) | Nightly, when the regression ends, and by hand | The hub (`cards-hub`, label `hub`): a small always-on cloud machine with the `claude` CLI, which runs no card tests | Gathers what the night's jobs did, and the cards added, changed, or removed on `main`, from GitHub (`.github/scripts/daily_report.py`), lists the actions for a person first, and adds a two-sentence summary from a small model | The pinned **Daily report** issue: its text is the latest report, and each day's is a comment that mentions the person in `REPORT_NOTIFY`, so GitHub emails them. Each report is also kept on the `reports` branch. A watchdog on GitHub's own runners (`daily-report-watchdog.yml`, 23:30 UTC) comments when a morning has no report, such as when the Mac was off |
| **site** ([site.yml](.github/workflows/site.yml)) | Every push to `main`, after each regression, daily at 20:00 UTC, and by hand | GitHub's own runners | card-kit's `card-site` builds the catalog site from the cards, the latest test results, and the needs map: a page per card, a page per need, `llms.txt`, and a sitemap. The build is a plain folder that works at any address, and each channel is a deploy job that takes it: GitHub Pages, and the `site` branch, which the [static-site](static-site) card serves as cards.edgible.org. The canonical address is the repository variable `SITE_URL` | [cards.edgible.org](https://cards.edgible.org) |
| **runner-check** ([runner-check.yml](.github/workflows/runner-check.yml)) | By hand, with the label that picks one machine (`edgible-test` by default, or `hub`) | That self-hosted machine | Proves a machine is ready: its runner, OS, memory, disk and tools; a one-line Claude session where `claude` is installed; and Docker and the Edgible device it tests on, where those are installed | The run's log |
| **skill-evals** ([skill-evals.yml](.github/workflows/skill-evals.yml)) | Daily at 13:07 UTC, which starts the night, and by hand | The hub (`cards-hub`, label `hub`), with the `claude` CLI signed in and the `edgible-mcp` server | Tonight's share of the skill's held-out prompts (each runs once a week, about N/7 a night), answered in read-only sessions with the skill and judged by a second session | The [`eval-results` branch](https://github.com/edgible-org/cards/tree/eval-results), and the **Skill eval report** issue, combining the last seven nights |

Lifecycle tests, evals, and the grow job never run from a pull request.

The night is one chain with one schedule: the skill evals start at 13:07 UTC (23:37 in Adelaide in summer), and grow, the regression, the daily report, and the site each start when the job before them ends. A run started by hand does not set off the next job. GitHub can start a scheduled run hours late, and then the whole night moves together, in the same order. Nothing about the schedule lives on the runner, so the runner can move to another machine, such as a cloud server, with no change here; and an outside scheduler can start the night instead, by starting skill-evals through GitHub's API. The jobs that use Claude come first, so the usage window each opens on the runner's subscription has closed before the working day. Grow skips a night when that night's evals stopped early, such as at the usage limit; the judge and grow's agent use a smaller model, and the answering sessions the default one. A pull request only gets the checks that need no Edgible account, on GitHub's runners. Everything that publishes apps runs from `main`, by schedule or by a maintainer's hand.

## Public and private

Everything about cards is public: the cards, the tools, the skill, its tests, the workflows, the test results, and the eval reports. Public results build trust, let anyone see what works today, and give people and AI assistants something to find and cite. They also mean a runner can be replaced at any time: all the state lives in the repos, not on the machine.

What stays private is only what would let someone act as Edgible:

- the runner's Edgible sign-in and its machine;
- tokens, API keys, and passwords, which never appear in a card, a test result, or a log;
- device names, hostnames, and organization ids, which `check-cards` refuses in `test.yml`;
- a small reserve of held-out eval prompts, kept unpublished so the scores can tell whether a model has learned the public ones.

### The self-hosted runner and pull requests

A runner that can publish apps must never run code from a pull request, because a pull request from a fork can change a workflow. So:

- the regression and eval workflows trigger only on `schedule` and `workflow_dispatch`, never on `pull_request`;
- workflow runs from outside contributors need a maintainer's approval (the repo's Actions setting for fork pull requests);
- the runner is registered to this repo only, and does nothing but these jobs.

## Where things are going

- **The regression moved here.** Until 2026-10-11 it ran from a private workflow, with its status kept privately. It now runs from [regression.yml](.github/workflows/regression.yml) in this repo and publishes to `test-status` directly. The serving device it publishes on is the machine's own: `TEST_DEVICE` in its runner's `.env`, or else the repository variable `TEST_DEVICE`, so no device name is in the file and each machine in a fleet tests on itself.
- **Pattern cards include app cards** with Compose `include:` rather than copying their services, so a fix to an app card reaches every pattern built on it.
- **The skill eval loop grows:** generated scenarios each week, and a scan for emerging needs (the MCP Registry, GitHub, self-hosting forums) that proposes needs-map entries as pull requests.
- **Platform primitives** the cards keep needing, such as tags for counting deployments, sign-in for MCP clients, and backup and restore, are tracked by Edgible.
